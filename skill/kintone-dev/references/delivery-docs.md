# 交付文件規範（每個開發案至少產出三份文件）

完成 kintone 客製化程式碼後，除了 .js 檔案本身，**必須同時產出以下三份 Markdown 文件**。三份文件的讀者不同、目的不同、用詞深度不同，不可互相複製貼上充數。

| 檔名 | 讀者 | 目的 |
|---|---|---|
| `CLAUDE.md` | 之後接手的 AI（Sonnet／Opus／未來的 Claude） | 讓 AI 不用重新摸索就能安全修改這支程式 |
| `TECHNICAL.md` | 技術人員（工程師、資訊部門） | 部署、維護、除錯所需的完整技術資訊 |
| `DESIGN-REVIEW.md` | 表單主要窗口（業務單位，非技術背景） | 確認需求理解正確，簽核後才進入正式環境 |

文字風格共同要求：
- 全部使用自然、正式的繁體中文。不使用機器翻譯腔的詞彙（例如不寫「解耦」，改寫「降低相依」；不寫「打平」「拉齊」這類詞）。
- 每個名詞第一次出現時，DESIGN-REVIEW.md 內要用一句白話解釋（例如「流程動作：畫面上『送審』『核准』這類按鈕」）。
- 程式碼註解遵守同樣原則：說明「這個變數／設定用在哪裡、改了會影響什麼」，而不是逐行翻譯程式在做什麼。

---

## 模板一：CLAUDE.md

```markdown
# CLAUDE.md — <App 名稱>（App ID: <ID>）客製化

## 這支程式在做什麼
<一段話講完：觸發時機 → 做什麼 → 結果。>

## 修改前必讀的限制
- 本專案所有事件處理遵守 kintone-dev skill 的規範：IIFE、const、safeHandler、CONFIG 集中設定。
- kintone.app.record.get()/set() 不可在 kintone.events.on() 處理函式本體內呼叫；change 事件處理函式不可為 async。
- process.proceed 內 return event 需要執行者具備編輯權限；本專案採「先查權限再決定是否 return event」寫法，不要改掉。

## CONFIG 結構說明
| 鍵 | 用在哪裡 | 改動影響 |
|---|---|---|
| FIELDS.<名稱> | <哪些事件、哪些函式引用它> | <欄位代碼改名時只改這裡> |
| ... | ... | ... |

## 事件對照表
| 事件 | 對應函式 | 行為 |
|---|---|---|
| app.record.create.show / edit.show / index.edit.show | applyFieldState | 依規則設定欄位顯示與 disabled |
| app.record.{create|edit}.change.<欄位> | applyFieldState | 與 show 共用同一套規則（單一事實來源） |
| app.record.{create|edit}.submit | validateOnSubmit | 存檔前驗證 |
| app.record.detail.process.proceed | validateOnProceed | 流程動作前驗證（含附件檢查） |

## 已知取捨與待辦
- <例如：change 內的跨 App 查詢採 .then() 延遲寫入，多程式並存時有覆蓋風險，詳見 TECHNICAL.md。>
```

## 模板二：TECHNICAL.md

```markdown
# <App 名稱> 客製化技術文件

## 環境資訊
- App ID：<ID>（正式）／<ID>（測試，如有）
- 檔案：<filename>.js，掛載於「JavaScript / CSS 自訂」電腦版與行動版
- 相依：SweetAlert2（Cybozu CDN）等，列出完整 URL
- 驗證方式：使用者登入 Session／API Token（Token 權限範圍寫明）

## 欄位代碼對照表
| 欄位顯示名稱 | 欄位代碼 | 類型 | 用途 |
|---|---|---|---|

## 功能規格
逐條列出：觸發事件 → 條件 → 動作 → 錯誤時的表現（畫面訊息原文）。

## 部署步驟
1. 上傳 js 至測試環境 → 2. 驗證清單（附測試案例）→ 3. 反映至正式環境。

## 除錯指引
- 事件沒觸發：先 console.log 確認 handler 有被呼叫（kintone 事件名拼錯不會報錯）。
- 無權限錯誤（process.proceed）：確認執行者記錄編輯權限，或檢查是否有其他程式碼未依「查權限再 return event」原則。
- 常見錯誤碼：GAIA_RE01（記錄不存在／無權限）、CB_AU01（Session 過期）、GAIA_TM12（速率限制）。

## 修改紀錄
| 日期 | 版本 | 修改內容 | 修改人 |
|---|---|---|---|
```

## 模板三：DESIGN-REVIEW.md（給表單主要窗口確認用）

寫作原則：**不出現程式碼、不出現事件名稱、不出現英文術語**。用「當使用者做了什麼 → 畫面會發生什麼」的句型，讓非技術窗口能逐條打勾確認。

```markdown
# <App 名稱> 自動化功能設計確認書

親愛的 <窗口姓名>：以下是這次要加入「<App 名稱>」的自動化功能說明，請逐項確認是否符合需求。有任何一項與您的想像不同，請直接在該項旁註記，我們修改後再請您確認一次。

## 一、這次要做的功能總覽
1. <白話一句：例如「送出表單前，系統會自動檢查必填欄位，漏填會擋下並提示」>
2. ...

## 二、逐項說明

### 功能 1：<名稱>
- 什麼時候發生：<例如「使用者按下『儲存』的當下」>
- 系統會做什麼：<條列>
- 使用者會看到什麼：<畫面訊息原文，逐字列出讓窗口確認措辭>
- ☐ 確認無誤　☐ 需要修改（備註：＿＿＿）

### 功能 2：……（同上格式）

## 三、需要窗口決定的事項
| 問題 | 選項 | 您的決定 |
|---|---|---|
| <例如：附件漏傳時的提示文字> | A：「請上傳報價單」／B：自訂 | |

## 四、上線時程
- 測試環境驗證：<日期>
- 預計正式上線：<日期>
- 確認簽名／回覆日期：＿＿＿＿
```

---

## 產出時機與檢查
1. 程式碼定稿後立即產出三份文件，放在與 .js 檔同一輸出目錄。
2. 自我檢查：DESIGN-REVIEW.md 給完全不懂程式的人看得懂嗎？CLAUDE.md 的 CONFIG 表格是否涵蓋每一個鍵？TECHNICAL.md 的畫面訊息是否與程式碼中的字串逐字一致？
3. 若使用者只要求程式碼、未提及文件，仍預設附上三份文件（可精簡），並提醒使用者這是本 skill 的交付標準。
